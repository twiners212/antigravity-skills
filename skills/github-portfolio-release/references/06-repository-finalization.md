# Phase 6 — GitHub repository finalization

**Mode:** inspect first; online repository settings and metadata changes require approval.

## Objective

Make the GitHub repository easy to understand and credible as a professional portfolio project.

## Review checklist

### Repository identity

- Clear repository name and concise description.
- Relevant topics/tags that describe the real project and stack; avoid keyword stuffing.
- Correct visibility and default branch.
- No confusing fork/template status or unrelated files at the top level.

### README landing page

- Accurate one-sentence summary and project purpose.
- Highlights of genuinely implemented features.
- Stack grouped by role, not an oversized collection of badges.
- Setup, environment, run, test, and build instructions verified against the repository.
- Architecture/structure overview proportional to project complexity.
- Real screenshots or demo link only when available and approved.
- Known limitations or incomplete features where material.
- Clear contact/contribution information only when the owner wants it.

### Supporting assets and legal choices

- Use optimized, genuine screenshots that reflect the current UI. Do not fabricate product shots, demo data, customer testimonials, or UI claims.
- Avoid large decorative assets that slow repository loading or add little value.
- Do not add a license automatically. Ask the owner to choose after explaining that public visibility does not itself grant reuse rights and a license changes reuse permissions.
- Do not publish environment files, data exports, user uploads, private design files, or internal notes.

### Repository consistency

- Check README links, headings, code blocks, screenshots, and instructions.
- Check that documentation matches the actual default branch and deployed version.
- Confirm release tags and GitHub Pages/configuration only if relevant.

## Applying changes

Prepare proposed metadata/content changes and identify whether each is local (README/docs) or remote (description/topics/branch/visibility/settings). Local documentation changes may be made within the authorized scope. Obtain approval before changing online repository settings or adding a license. For README changes, inspect and validate the diff before committing/pushing.

## Required report

Summarize the GitHub landing-page quality, verified items, proposed/applied metadata, missing assets/links, license decision, and remaining polish. Do not claim the repo is recruiter-ready solely because its README has badges or screenshots.
